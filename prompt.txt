# Перед началом

1. Проверь, что `<TASK-ID>` существует.
2. Проверь, что все её зависимости имеют статус `done`.
3. Выпиши для себя:
   - цель;
   - scope;
   - что находится вне scope;
   - критерии приёмки;
   - обязательные проверки;
   - затрагиваемые модули.
4. Выполни `git status --short`.
5. Отдели существующие изменения пользователя от изменений этой задачи.
6. Не откатывай и не перезаписывай пользовательские изменения.
7. Если зависимость задачи не завершена, не начинай реализацию и сообщи об этом.

# Границы

Выполняй только `<TASK-ID>`.

Разрешены только изменения, необходимые для выполнения её критериев приёмки.

Запрещено:

- начинать другую backlog-задачу;
- выполнять попутный рефакторинг;
- исправлять несвязанные проблемы;
- менять утверждённый scope;
- обновлять зависимости без доказанной необходимости;
- менять архитектуру без требования задачи;
- обращаться к production DB, Blob или другим production-ресурсам без явно зафиксированного разрешения;
- помещать secrets в код, документацию, logs или итоговый ответ;
- создавать коммит;
- переключать ветки;
- выполнять `git reset`, `git clean`, `git stash`, `git merge` или `git rebase`.

Если обнаружена проблема вне scope:

- не исправляй её;
- зафиксируй как наблюдение;
- укажи, блокирует ли она текущую задачу.

# Архитектура агентов

Сначала оцени полезность субагентов.

Используй субагентов только если задача содержит независимые направления, которые можно безопасно исследовать параллельно без одновременного редактирования одних файлов.

Не используй субагентов для узкой линейной задачи.

Если субагенты используются:

- главный агент принимает все решения и интегрирует изменения;
- субагенты не создают вложенных агентов;
- субагенты не принимают финальное решение;
- субагенты не редактируют одни и те же файлы;
- каждый субагент получает только необходимый контекст;
- главный агент перепроверяет их выводы.

# Реализация

1. Исследуй относящиеся к задаче файлы и callers.
2. Подтверди реальную причину каждого изменения.
3. Внеси минимальный целостный набор изменений.
4. Сохраняй существующий стиль и архитектуру.
5. Не маскируй ошибки отключением проверок, подавлением diagnostics или фиктивными реализациями.
6. После каждого существенного изменения выполняй наиболее узкую относящуюся проверку.
7. После локальных проверок выполни полный набор проверок задачи.
8. Продолжай до выполнения всех критериев либо до доказанного блокера.

Не останавливайся после первого частичного успеха.

# Блокировка

Остановись и запроси решение владельца только если:

- требуется изменить утверждённый продуктовый scope;
- требуется необратимое или потенциально опасное действие;
- необходим недоступный credential, backup, внешний ресурс или production access;
- требуется существенное изменение архитектуры;
- необходимо значительное обновление зависимостей;
- существуют несовместимые варианты без доказанного приоритета;
- пользовательские изменения невозможно безопасно совместить с обязательным исправлением.

Перед остановкой:

1. Проверь доступные безопасные варианты.
2. Подтверди blocker конкретной диагностикой.
3. Не применяй опасный обход.
4. Укажи минимальное решение, требуемое от владельца.

# Проверка результата

Выполни:

- проверки из строки `<TASK-ID>` в backlog;
- относящиеся проверки из `06_VALIDATION_PLAN.md`;
- проверки затронутых модулей;
- `git diff --check`;
- проверку изменённых файлов на secrets;
- проверку итогового diff;
- проверку отсутствия несвязанных изменений.

Не утверждай, что проверка прошла, если она не запускалась.

Для каждой проверки укажи:

- команду или сценарий;
- результат;
- exit code, если применимо;
- что именно она доказывает.

# Evidence

Создай или обнови:

`docs/implementation/evidence/<TASK-ID>.md`

В evidence зафиксируй:

- цель задачи;
- исходное состояние;
- затронутые файлы;
- принятые решения;
- выполненные изменения;
- выполненные команды;
- результаты проверок;
- невыполненные проверки и причины;
- найденные проблемы вне scope;
- итог по каждому критерию приёмки.

Не вставляй длинные сырые logs и секреты.

# Обновление состояния

Только после выполнения всех критериев приёмки:

1. Измени статус `<TASK-ID>` в `docs/implementation/04_BACKLOG.md` на `done`.
2. Обнови `docs/implementation/09_STATE.md`:
   - выполненную задачу;
   - фактические проверки;
   - новые подтверждённые факты;
   - активный milestone;
   - следующую незаблокированную задачу.
3. Обнови `docs/implementation/00_INDEX.md`, если создан новый evidence-документ.
4. Обнови другие документы только если они стали фактически неверными.

Если обязательный критерий не выполнен:

- не ставь `done`;
- зафиксируй blocker;
- оставь задачу текущей;
- не переходи к следующей.
